## Why plan 006 was shipped first

The operator asked for one PR containing either the highest-leverage feature grounded in repo evidence or a substantial correctness fix. Plan 006 was chosen for four reasons:

- **The repo asks for it.** It is the roadmap's only "Now" item, and `ROADMAP.md` spells out the slice: "Add one weekly-review resource/tool that composes existing reads and includes a coverage matrix, not a new scoring model."
- **Nothing like it exists.** Grepping for `week`, `review` and `coverage` in `src/` finds nothing relevant.
- **It is cheap to build.** It reuses the day tool's permission and availability model, so it can be verified completely with the existing Worker tests.
- **It beats the next candidate.** Plan 007 is a real bug, but it is smaller, and it depends on Garmin's resend reusing the same `activityId`. That has not been observed (confidence MED).

The roadmap says to collect the pilot baseline before building this slice. That baseline has not been collected; `ROADMAP.md` now records this.

## Direction suggestions (options, not ranked against bugs)

- **Week view in MCP Apps.** The day and activity views exist (`src/mcp-apps/views.ts`). A 19×7 coverage grid would make missing dates obvious. Effort M. Trade-off: one more view to keep in sync, plus browser tests.
- **Planned-versus-completed follow-up** (roadmap "Next"). `scheduleResponse` already carries `{scheduleId, workoutId, date}`. Matching needs `get_workout` for each schedule to learn the sport, and has to label uncertain matches. Effort M–L.
- **Expected-category coverage.** Plan 006 treats a date without `dailies` as missing. Categories like blood pressure are occasional, so a per-category "expected daily" notion would need product input. Wrong defaults would hide real sync gaps. Effort S once decided.
- **Usage baseline.** The roadmap's repeat-use gate cannot be measured from the system. A fixed-label tool-call log line would work, but counting distinct users is a privacy trade-off for the maintainer. Effort S.

## Findings considered and rejected or deferred

- **Cache Garmin permission lookups per request**: rejected. The per-call lookup is documented by design (`docs/garmin-training.md`), and the post-I/O recheck is a deliberate safety property.
- **Avoid `bindActivityOwner` on every `/mcp` request**: rejected; by design (first run).
- **Give the `activate` control action its own credential**: deferred. Auth can lift a tombstone with the push delivery credential. Exposure is modest, because a holder of that credential can already forge data for accounts that were never revoked. A fix needs a coordinated change in the Auth repo. The first run's rationale ("disconnect adds no new power") does not cover `activate`.
- **Deregistration arriving after `activate()` re-revokes the account**: deferred. Deregistrations carry no timestamp, so a fix needs a design decision (for example, ask Garmin before tombstoning). Plan 009 fixes only the timestamped half.
- **Split `src/events/store.ts` (763 lines)**: not worth doing now. The ordering of checks around awaits is load-bearing, and the missing tests (finding 8) should come first.
- **Unify credential and permission authorization across five sites**: deferred until finding 8's tests exist, since the mismatch semantics differ on purpose (revoke versus deny).
- **Pin TypeScript to stable 7.0.x instead of the nightly**: maintainer decision; no 7.1-only dependency was checked.
- **CI builds MCP Apps four times**: low value while CI cannot run at all.
- **`portless` dev port versus `PUBLIC_URL`, and missing `.dev.vars.example`**: plausible (MED confidence), not verified by running `pnpm dev`.
