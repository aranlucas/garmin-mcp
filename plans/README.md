## Findings without a plan

These were confirmed against the code but need a maintainer decision, or rank below the five above.

- **Activity tools return complete time series to the model.** `get_garmin_activity` and `get_garmin_summary` return every decoded FIT message (bounded at 8 MiB, `src/activity/fit.ts:12`) plus JSON activity details, and `toolResult` (`src/tool-result.ts:9-14`) serializes the whole payload a second time into the text `content`. The repo's own test shows 12,000 samples exceed 2 MiB (`test/activity.test.ts:210-250`), which is far beyond any model context. `list_garmin_summaries` with `type: "activityDetails"` returns full sample arrays for up to 100 records. The views read only `structuredContent`. This collides with the documented decision to expose complete FIT data (`docs/strength-activity-files.md`), so it needs a product call: for example a compact default with an explicit detail selector, or a digest in `content` with the full data kept in `structuredContent`.
- **A single oversized summary blocks its batch.** `summaries.data` is one `TEXT` value (`src/push/store.ts:109-118`). A record above SQLite's per-value limit fails the whole `ingest` transaction, the receiver answers `500`, and Garmin retries the same batch. Decoded FIT data is already chunked for this reason (`src/activity/store.ts:21`). Needs a decision: chunk large summaries, or drop them with a log line.
- **`get_garmin_day` makes 20 Durable Object calls.** `src/day.ts:42-56` calls `store.isRevoked()` and then `store.list()` once per category. One store method that returns the whole day would cut round trips and read a consistent snapshot. Effort S–M.
- **The generated wellness client is unused.** Nothing imports `src/garmin-api/wellness/` (about 4,600 lines). The push envelope in `src/push/schemas.ts` is hand-written and had drifted from the generated models (Plan 001). Either generate only its Zod schemas and use them for per-category contract tests, or stop generating the SDK part.
- **MCP surface polish.** Tools have no `title` and no `outputSchema`, although `get_garmin_day` already validates its result against a Zod schema (`src/day.ts:23-35`). Training annotations are derived from the tool name prefix (`src/training/mcp.ts:47-52`), so `delete_*` and full-replace `update_*` tools report `idempotentHint: false`. `createServer` builds two `TrainingClient` instances (`src/mcp.ts:72-73`). The server reports version `2.0.0` while `package.json` says `1.0.0`. Low impact each.

## Findings considered and rejected

- A Garmin permission lookup on every tool call (two Garmin requests per Training call): by design. `docs/garmin-training.md` says "Validate `WORKOUT_IMPORT` on each tool call", and `README.md` says each Health/Activity read checks current permissions.
- The delivery credential in the webhook URL path, also used for `/garmin/disconnect` and as the key-derivation input for event secrets: by design and documented in `README.md` (Garmin's configuration tool has no header field). A holder of that credential can already send deregistrations, so the disconnect route adds no new power.
- FIT limits of 1 MiB, 25,000 messages and a consumed one-use URL on failure: documented decisions in `docs/strength-activity-files.md` and `docs/authorization-retention.md`. Very long activities will fall outside them; watch the `download_failed` state rather than changing the bounds blind.
- Rejecting a whole delivery when one record is invalid: recorded as intentional "validation before mutation" in `docs/reliability-audit.md`. Plan 002 makes it observable instead.
- The Auth broker call and `bindActivityOwner` on every `/mcp` request, including `initialize` and `tools/list`: by design, so a disconnected account gets `401` on any request and pending file downloads are bound.
- Event subscription, delivery, retry and secret handling in `src/events/`: reviewed at reading depth only. The 2026-11-06 reliability audit covered it and nothing new stood out.
